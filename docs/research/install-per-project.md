# How one private skills repo installs into each project (Claude Code and Cursor)

Ticket: #7. All web sources read 2026-10-13. Local files were read the same day.

Doc URLs below are short forms. `CC` = `https://code.claude.com/docs/en/`. `CU` = `https://cursor.com/docs/`.

## Short answer

**For "Does Friday use upstream skills in place or copy and own them?"**

- Claude Code has a native way to use upstream skills in place. Friday can list the upstream marketplaces (`mattpocock/skills` is already one) and enable their plugins per project. Updates then come from upstream, and Friday owns nothing. Friday can also own a fork or copy as a plugin in its own marketplace.
- The cost of "in place" is that plugin skills are namespaced (`/mattpocock-skills:tdd`). `skillOverrides` does not apply to plugin skills, so single skills inside a plugin cannot be switched off. Switching is per plugin only (CC `skills`, "Override skill visibility"). The finest unit of per-project switching is the plugin, so a copy that Friday owns can be split into small plugins, which in-place use cannot do.
- Emil's paid skills are already plain folders in `~/.claude/skills`, loaded in every project. Both Claude Code and Cursor read that folder (see the table). I found no licence text, so I could not verify whether Friday may copy or republish them. Treat them as "use in place, never commit into a repo" unless the licence says otherwise.
- pstack lives at `github.com/cursor/plugins/tree/main/pstack`, which is Cursor's plugin format. I did not verify that Claude Code can install it directly. Cursor reads `.claude/skills` and Claude Code reads `SKILL.md`, so its skills are probably usable by copying, but this was not checked.

**For "How does Friday install into a project?"**

- Best fit for Claude Code: make `somyanath/friday` (private) a plugin marketplace, with Friday's skills, subagents, hooks and commands in plugins inside it. Add it once at user scope. It authenticates with the git credentials already on the machine, and no token goes in the repo (CC `plugins/host-marketplace`, "Grant access to a private marketplace").
- Enable plugins per project in that project's `.claude/settings.local.json` (local scope). Claude Code adds that file to the global git excludes the first time it writes it, so a public project never receives the entry. Local overrides project, which overrides user (CC `discover-plugins`, "Choose an install scope"). Keep Friday plugins disabled (`false`) in `~/.claude/settings.json`, or just leave them unset, so they are off elsewhere.
- Do not use the project scope (`.claude/settings.json`) for Friday's plugins in public repos. It is committed and would publish the plugin name and the private marketplace's repo name.
- Cursor reads `.claude/skills` and `~/.claude/skills` natively (CU `skills`), so skills placed or symlinked there work in both tools. Cursor cannot use a private Claude marketplace. Its plugin route needs a `.cursor-plugin/marketplace.json` and a team marketplace, which is a Teams or Enterprise feature. The public Cursor marketplace requires plugins to be open source (CU `plugins`).
- So the workable shape for both tools is two layers. (a) A Claude Code plugin marketplace for plugins, hooks, subagents and updates. (b) A small install script that symlinks chosen skill folders into a project's `.claude/skills/` and excludes them via `.git/info/exclude`, which serves Cursor and any session where plugins are unavailable. Layer (b) is my design suggestion, built from documented pieces and not tested here.
- `AGENTS.md` and `CLAUDE.md`: Friday should not add either to a public project. Put Friday's cross-project rules at user level (`~/.claude/CLAUDE.md` or `~/.claude/rules/`), and per-project Friday notes in the gitignored `CLAUDE.local.md`.

## Detail and sources

### Claude Code: plugins and marketplaces

- A plugin is a directory with skills, agents, hooks, MCP servers and other components, installed as one unit. Components are skills (`skills/`), commands (`commands/`), agents (`agents/`), hooks (`hooks/hooks.json`), MCP servers, LSP servers, executables, themes and monitors. [CC `plugins`](https://code.claude.com/docs/en/plugins), [CC `plugins/components`](https://code.claude.com/docs/en/plugins/components), read 2026-10-13.
- Plugin agents support `name, description, model, effort, maxTurns, tools, disallowedTools, skills, memory, background, omitClaudeMd, isolation, color`. They ignore `permissionMode`, `hooks` and `mcpServers` in frontmatter, so those must be plugin-level. Same page. Of the plugin-level settings, only `agent` and `subagentStatusLine` take effect, and user settings override them.
- Plugin skills are invoked as `/plugin-name:skill-name` ([CC `skills`, "Choose where skills load"](https://code.claude.com/docs/en/skills), read 2026-10-13). That namespace is why a Friday skill and an upstream skill with the same name do not collide.
- A marketplace is a repo with a catalog. Entries can be relative paths inside the repo, or `github`, `url`, `git-subdir` and `archive` sources. [CC `plugin-marketplaces`](https://code.claude.com/docs/en/plugin-marketplaces), read 2026-10-13. A relative-path plugin needs no separate install record, because it loads from the marketplace itself ([CC `plugins/loading`](https://code.claude.com/docs/en/plugins/loading), "Enabled in project settings but not installed").
- **Private repo as marketplace: yes.** "The repository can be private" ([CC `plugin-marketplaces`](https://code.claude.com/docs/en/plugin-marketplaces)). Claude Code runs `git` on the user's machine with prompts turned off and uses credentials already there. It has no git token of its own, and `marketplace.json` has no field for one. For GitHub `owner/repo` it tries SSH first, then HTTPS. For HTTPS, `gh auth login` then `gh auth setup-git` stores a working credential. `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` skips the SSH probe. A `GITHUB_TOKEN` in the environment alone does not authenticate the background check; it takes effect only through a credential helper such as `gh`'s. [CC `plugins/host-marketplace`, "Grant access to a private marketplace" and "What background auto-update does with credentials"](https://code.claude.com/docs/en/plugins/host-marketplace), and [CC `discover-plugins`, "Add a private marketplace"](https://code.claude.com/docs/en/discover-plugins), read 2026-10-13.
- Local check: `~/.claude/plugins/known_marketplaces.json` already lists `mattpocock` (`github`, `mattpocock/skills`) and three others. `installed_plugins.json` shows `mattpocock-skills@mattpocock` 1.3.1, installed at `scope: "user"`. `~/.claude/settings.json` has `enabledPlugins` for figma, warp, mattpocock-skills and cache-tax, and `extraKnownMarketplaces` for three of the four.
- Upstream marketplaces can be listed in `extraKnownMarketplaces` (seen in the local `settings.json`). That setting declares them, and installing is a separate step. [CC `discover-plugins`](https://code.claude.com/docs/en/discover-plugins), read 2026-10-13.

### Claude Code: scopes and per-project switching

- Plugin scopes: **user** (`~/.claude/settings.json`, every project), **project** (`.claude/settings.json`, committed, everyone), **local** (`.claude/settings.local.json`, you in this repo only). Local overrides project, and project overrides user. [CC `discover-plugins`, "Choose an install scope"](https://code.claude.com/docs/en/discover-plugins), read 2026-10-13.
- `enabledPlugins` resolves per plugin id from six sources (lowest to highest): `--add-dir`, user, project, local, `--settings` flag, managed. The highest source that mentions the id wins. To opt out of a project-enabled plugin, set it to `false` in `.claude/settings.local.json`. [CC `plugins/loading`, "Find where a plugin is enabled"](https://code.claude.com/docs/en/plugins/loading), read 2026-10-13.
- Claude Code fetches an externally sourced plugin onto a machine only when the `true` comes from user settings, an untracked `.claude/settings.local.json`, the `--settings` flag or managed settings. A `true` that exists only in a committed project file is not fetched. Same page. For Friday this means a project cannot pull Friday in just by being cloned, which is the right behavior for public repos.
- `claude plugin install <p>@<m> --scope local|project|user` (default `user`). `enable` and `disable` act on the most specific scope that already lists the plugin. [CC `discover-plugins`, "Manage plugins from your shell"](https://code.claude.com/docs/en/discover-plugins), read 2026-10-13.
- **`settings.local.json` and git.** The first time Claude Code writes the file in a git repo that doesn't already ignore it, it adds `**/.claude/settings.local.json` to the global git excludes file. If you create the file by hand, add it to `.gitignore` yourself. [CC `settings`, "Keep personal settings out of a repository"](https://code.claude.com/docs/en/settings), read 2026-10-13. Local check: `~/.config/git/ignore` contains `**/.claude/settings.local.json`, and `git check-ignore -v` in `/Users/somyanath/Portfolio` reports that file as ignored through it. Portfolio's own `.gitignore` has no `.claude` entry (it has `*.local`, `notes/`, etc.), so the project relies on that global exclude. A fresh clone on another machine would not have the exclude until Claude Code writes the file there.
- **`skillOverrides`** takes `on`, `name-only`, `user-invocable-only`, `off` per skill name, in user, project or local settings. The `/skills` menu writes it to `.claude/settings.local.json`. It applies to personal and project skills only, not to plugin skills, which are managed through `/plugin`. [CC `skills`, "Override skill visibility from settings"](https://code.claude.com/docs/en/skills), read 2026-10-13. Local check: `~/.claude/settings.json` uses it for `anthropic-skills:skill-creator` and `anthropic-skills:web-animation-design` (both `off`). Whether a name containing a colon is matched exactly by the docs' rule ("matches entries against skill names only") is not stated; the local file suggests it works for synced skills, but I did not test it.
- **Skill locations**: enterprise, personal (`~/.claude/skills`), project (`.claude/skills`), nested (`<subdir>/.claude/skills`), `--add-dir`, plugin, claude.ai account. A `<skill-name>` entry in enterprise, personal or project location can be a symlink to a directory elsewhere on disk, and a skill reached through several links loads once. Plugin skills handle symlinks differently. [CC `skills`, "Choose where skills load"](https://code.claude.com/docs/en/skills), read 2026-10-13.
- **Plugin symlinks**: when a plugin is copied into the cache, a symlink inside the plugin's own directory is kept, a symlink to elsewhere in the same marketplace is dereferenced (content copied), and one pointing outside the marketplace is skipped. So a plugin cannot link to a separate checkout of Friday. Instead, put the plugins in the Friday repo and link between them. [CC `plugins/host-marketplace`, "Share files within a marketplace with symlinks"](https://code.claude.com/docs/en/plugins/host-marketplace), read 2026-10-13.
- **Name conflicts**: same-named plugins resolve by origin (managed, then `--plugin-dir`, then installed, then skills-directory plugin, then claude.ai sync). A `--plugin-dir` plugin silently replaces an installed plugin of the same manifest name. [CC `plugins/loading`, "Name conflicts"](https://code.claude.com/docs/en/plugins/loading), read 2026-10-13. This makes `--plugin-dir ~/friday/plugins/x` a handy live-development override while Friday is being built.
- Two same-named plugins from different marketplaces both show enabled, but only one registers its hooks. Same page. Avoid reusing upstream names in Friday's plugins.

### Claude Code: how updates flow

- Auto-update is on by default only for Anthropic's official marketplaces. A private or third-party marketplace like Friday's or Matt Pocock's is off until turned on in `/plugin`, Marketplaces tab, or by `autoUpdate: true` on its `extraKnownMarketplaces` entry. [CC `discover-plugins`, "Keep plugins updated"](https://code.claude.com/docs/en/discover-plugins), [CC `plugins/loading`, "When auto-update runs"](https://code.claude.com/docs/en/plugins/loading), read 2026-10-13.
- When on: after the first message of a session, a random delay of up to ten minutes, then marketplaces refresh and installed plugins update on disk. The running session keeps the version it loaded (`/reload-plugins` applies it); the next launch gets the new one. Same page.
- A new copy arrives only when the computed version changes: `plugin.json` version, else the marketplace entry version, else the commit SHA (12 chars) for git sources. If `version` is set and not bumped, pushed commits do not reach users. Omit `version` to track every commit. Don't set it in both places. [CC `plugins/host-marketplace`, "Release a new version"](https://code.claude.com/docs/en/plugins/host-marketplace), read 2026-10-13. Recommendation for Friday: omit `version` while iterating.
- A plugin loaded in place from a marketplace added from a local path always loads current files at session start. Same page. So a marketplace added from a local checkout of Friday (`/plugin marketplace add ~/friday`) gives live edits with no push, but then it is no longer fetched from GitHub on other machines.
- Private background updates: SSH needs the key in `ssh-agent`. HTTPS needs a credential helper that already holds a credential (`gh auth setup-git`, macOS Keychain). If it can't authenticate, Claude Code re-clones; if that fails, the old checkout stays. `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1` skips the re-clone. [CC `plugins/host-marketplace`](https://code.claude.com/docs/en/plugins/host-marketplace), read 2026-10-13.

### Claude Code: CLAUDE.md, rules and layering

- Load order, broadest to most specific: managed, user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md` or `./.claude/CLAUDE.md`), local (`./CLAUDE.local.md`, gitignored). All discovered files are concatenated, not overridden, and what loads later is read last. `CLAUDE.md` and `CLAUDE.local.md` are loaded from the working directory and every directory above it; subdirectory ones load on demand. [CC `memory`](https://code.claude.com/docs/en/memory), read 2026-10-13.
- Contradictory instructions: "Claude may pick one arbitrarily." Same page. So a Friday rule must not contradict a project rule; it must defer.
- `@path` imports work in CLAUDE.md. `CLAUDE.local.md` is per worktree; to share personal instructions across worktrees, import a file from the home directory. `.claude/rules/*.md` loads recursively, can be path-scoped, and supports symlinks (an approval dialog appears once per project for project-level links; `~/.claude/rules/` has none). `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` makes `--add-dir` directories load their CLAUDE.md and rules too. Same page.
- `AGENTS.md`: read only when there is no `CLAUDE.md` or `CLAUDE.local.md` in the working directory or above; `~/.claude/CLAUDE.md` and `.claude/rules/` do not count for that check. Needs Claude Code v2.1.277 or later. Same page. So adding a `CLAUDE.local.md` to an `AGENTS.md`-only project would stop Claude Code reading that project's `AGENTS.md` unless the local file imports it. (The doc's "Share one file with other coding tools" section covers the import. I did not test the exact behavior.)
- `claudeMdExcludes` can skip files by glob at any settings layer. Same page.

### Cursor: skills and plugins

- Cursor supports the Agent Skills open standard with the same `SKILL.md` + frontmatter shape (`name`, `description`, optional `paths`, `disable-model-invocation`, etc.). Skills are discovered automatically from `.agents/skills/`, `.cursor/skills/` (project), `~/.agents/skills/`, `~/.cursor/skills/` (user) "For compatibility, Cursor also loads skills from Claude and Codex directories: `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/`, and `~/.codex/skills/`." Nested `.cursor/skills` folders in subdirectories are scoped to files under them. [CU `skills`](https://cursor.com/docs/skills), read 2026-10-13.
- That means Emil's skills in `~/.claude/skills` are visible to Cursor already, and any Friday skill folder placed or symlinked into `.claude/skills` serves both tools. Differences to watch: Cursor requires `name` to match the folder name and uses lowercase letters, numbers and hyphens (same page). I did not check Emil's skills against that rule.
- Cursor does not copy `~/.agents/skills/` or unsynced local skills to Cloud Agents, remote SSH sessions or self-hosted workers. User skills in `~/.cursor/skills/` can be synced to the user's own Cloud Agents (setting "Sync Skills for Cloud Agents"). Same page. Project skills must be in the repo for cloud runs. This matters for Fleet and Unattended runs on cloud agents: Friday's skills would have to be in the repo, which public projects cannot do. Unresolved, noted for the unattended-runs question.
- Skill import: "Skills aren't imported on their own." To bring skills from a GitHub repo, package them as a plugin in a repo with `.cursor-plugin/marketplace.json` and import it in Customize via "From GitHub Repository", or add it as a team marketplace. [CU `skills`](https://cursor.com/docs/skills), read 2026-10-13. Whether "From GitHub Repository" works for a private repo on a non-team plan is not stated; I could not verify it.
- Plugins: two formats. Agent Plugins (root `plugin.json`, skills and MCP only) and Cursor Plugins (`.cursor-plugin/plugin.json`, adds rules, agents, commands, hooks). Install scope is project or user. The marketplace lists reviewed plugins, and "All plugins must be open source". Team marketplaces are for Teams (1) and Enterprise (unlimited), imported from GitHub, GitLab, Bitbucket or Azure DevOps. Plugins index at import, refresh manually or on push with the Cursor GitHub App. Local testing: `~/.cursor/plugins/local/<plugin>`, where symlinks load only if the target is inside that folder, and Teams and Enterprise admins control "Allow Local Plugin Imports". A `workspaceOpen` hook can return plugin paths to load when a workspace opens. [CU `plugins`](https://cursor.com/docs/plugins), read 2026-10-13. Plan and price for a Teams marketplace: not in these pages; it competes with the Rs 3000 per month cap, so the subscription ticket should price it before it is relied on.
- Claude Code plugin format is not stated to load in Cursor, and the reverse. Cursor's docs only mention the Agent Plugins standard as portable. I found no Claude Code doc statement on loading Agent Plugins.

### Cursor: rules, AGENTS.md, CLAUDE.md, hooks

- Project rules live in `.cursor/rules/*.mdc` (a plain `.md` is ignored). Types: Always, Apply Intelligently (description), Apply to Specific Files (globs), Apply Manually. [CU `rules`](https://cursor.com/docs/rules), read 2026-10-13.
- `AGENTS.md` is supported in the project root and subdirectories; nested ones combine with parents, "more specific instructions taking precedence". Same page.
- Precedence: "Team Rules, then Project Rules, then User Rules. All applicable rules are merged; earlier sources take precedence when guidance conflicts." User Rules are global, set in Customize and not stored on the file system. Same page. In Cursor, a user-level Friday rule would therefore lose to a project rule when they conflict, which is the same outcome Friday wants.
- Whether Cursor reads `CLAUDE.md`: **not stated in the Cursor docs pages I read** (`rules`, `skills`, `plugins`). The only first-party mention is that a setting "Include Third-Party Plugins, Skills, and Other Configs" (Settings, Agents, Third-Party Imports, on by default) loads Claude Code hooks from `.claude/settings.local.json`, `.claude/settings.json` and `~/.claude/settings.json`. [CU `reference/third-party-hooks`](https://cursor.com/docs/reference/third-party-hooks), read 2026-10-13. Cursor forum posts say the same toggle also picks up `CLAUDE.md` and `.claude/skills/`, but not `.claude/rules/` ([forum: .claude project level rules not loaded](https://forum.cursor.com/t/claude-project-level-rules-not-loaded-with-the-include-third-party-toggle-enabled/157087), read via search excerpt 2026-10-13). That is community evidence, not documentation, so treat `CLAUDE.md` in Cursor as unverified. Another forum thread reports that ignoring CLAUDE.md in `.cursorignore` isn't respected while that toggle is on (excerpt only).
- Hook layering in Cursor, highest to lowest: enterprise, team, project `.cursor/hooks.json`, user `~/.cursor/hooks.json`, then Claude project local, Claude project, Claude user. All matching hooks run. [CU `reference/third-party-hooks`](https://cursor.com/docs/reference/third-party-hooks). So Friday hooks written for Claude Code in `~/.claude/settings.json` also run in Cursor with the toggle on. Matcher names differ (the example matches `Shell`); I did not check how Claude tool names such as `Bash` map.

### How Friday's per-project layer sits beside Portfolio's CLAUDE.md

Read from `/Users/somyanath/Portfolio/CLAUDE.md` (67 lines). Its rules:
- Ask before committing, pushing, closing issues or PRs, force-pushing, and moving files.
- Specs are GitHub issues; no code before a reviewed spec.
- Conventional commits with scope and issue number, for example `feat(design-system): button primitive (#7)`.
- Per-app `apps/<app>/design.md` holding interface guidelines and a motion table, with tokens from `packages/design-system/tokens.css` as the only source.
- Stack facts: pnpm monorepo, React + Vite + Tailwind v4 in `apps/*`, CSS Modules in the design system, buildless HTML/CSS/JS in `challenges/*`.
- `notes/` is gitignored and not to be copied into tracked files. The repo is public.
- It has an "Agent skills" section pointing at `docs/agents/issue-tracker.md` and `docs/agents/domain.md`, which the Matt Pocock skills read.

Ways Friday can sit beside it without conflict:

1. **Nothing of Friday goes in the project's tracked files.** Friday arrives as plugins (method 1) or user-level files, both outside the repo. Portfolio's CLAUDE.md stays the single project authority. This also satisfies "nothing public may contain Friday's files" from the map.
2. **Friday states precedence once, at user level.** One line in `~/.claude/rules/friday.md` (user-level rules load for every project without an approval dialog): "A project's own CLAUDE.md or AGENTS.md decides stack, commits, approvals, doc locations and file layout. Friday's process adds gates; it never overrides a project's 'ask before' list." Because project CLAUDE.md loads after user-level files, the project's text is read last, which is the favorable position (CC `memory`). This only works if the Friday text really contains no contradiction, since Claude may pick either of two conflicting instructions.
3. **Friday's skills ask the project instead of assuming.** Where the design process needs a stack, a token file, a commit style or a place for the design language, skills should read the project's rules. For Portfolio, the design-language artifact for a surface maps onto `apps/<app>/design.md` (guidelines plus the motion table), so Friday should write there rather than inventing a second file.
4. **Gates stay additive.** Friday's Direction, Variant and Ship gates are about Somya's approval of design. Portfolio's "ask before committing or pushing" still applies on top, so a Fleet agent working in this repo should stop at a commit and not push, unless Portfolio's rule is changed. This is an interaction to put in front of the parallel-work ticket.
5. **Per-project Friday notes (which surfaces exist, which plugins are on) go in `CLAUDE.local.md`** (gitignored, loaded after `CLAUDE.md`). Portfolio's `.gitignore` does not list `CLAUDE.local.md` today, so the install step would need to add it to `.git/info/exclude` (local-only, from [git `gitignore` docs](https://git-scm.com/docs/gitignore), read 2026-10-13), not to the tracked `.gitignore`. Caution: in an `AGENTS.md`-only project, creating `CLAUDE.local.md` turns off direct reading of `AGENTS.md` (see the layering notes above).
6. **Cursor.** Portfolio has no `AGENTS.md` and no `.cursor/` today (I listed the repo root). In Cursor, Friday's skills arrive through `~/.claude/skills` or user-level skills, and Friday's always-on text through User Rules in Customize, which lose to project rules when they conflict. Nothing needs to be added to the repo.
7. **Skill-name collisions.** Portfolio has none of its own skills (`.claude` there only holds `settings.local.json`). In general, a project skill and a personal skill with the same name resolve by location order (CC `skills`, "Resolve skills that share a name"; I did not read the precedence table in full). Prefix Friday's own skills, for example with a plugin name, so the question does not come up.

### Keeping private and paid skills out of public repos

- Paid skills (Emil's): live in `~/.claude/skills` (user home, outside any repo) and Cursor reads that folder too. A symlink from a project's `.claude/skills/` into it should be excluded locally; a committed symlink would publish only the link and not the content, but it would reveal the skill names. `AIFORUI_TOKEN` is an environment variable and no config should store it. I did not open any token value.
- Which file holds which secret-ish thing: `.claude/settings.local.json` (gitignored via the global exclude) is the place for per-project Friday enablement. `.claude/settings.json` is committed and is not.
- `.git/info/exclude` is per clone, and not shared or committed ([git docs](https://git-scm.com/docs/gitignore)). A fresh clone needs the install script run again.
- Claude Code never prompts for git credentials during marketplace operations, so a missing credential on a new machine shows up as a failed add or silent stale plugins, not a prompt (CC `plugins/host-marketplace`).
- A user-scope plugin installed from the private marketplace is cached under `~/.claude/plugins/cache/...` (see the local `installPath` values), outside every repo.
